# 工程优化分析

对 `qc_agent` 全量代码（17 个模块 / 5 个脚本 / 4381 行）的审查结论。所有问题都附可复现的实测数据，
不做「看起来可以更好」的空泛建议。

基准环境：Python 3.12.3，本仓库 `742961c`，全部 75 项单测通过（2.85s）。

---

## 1. 已修复的问题

### 1.1 LLM 故障期的降级结论被写入缓存（P0）

`agent.py` 原先以 `res.source.startswith("llm")` 判断是否可缓存。当 LLM 返回不可解析内容
（供应商抖动、输出被 `max_tokens` 截断）时，`_finalize` 回退启发式并把 `source` 置为
`llm+heuristic` —— 该串同样以 `llm` 开头，于是降级结论被写进缓存。

复现（`BrokenLLM` 持续返回不完整 JSON）：

```
修复前  A. LLM 故障期结果 source='llm+heuristic' -> 是否写入缓存=True
        LLM 恢复后重跑 -> 命中缓存(未调用LLM)=True   # 降级结论被永久复用
修复后  A. LLM 故障期结果 source='llm+heuristic' -> 是否写入缓存=False
        LLM 恢复后重跑 -> 调用LLM=True  source='llm-fast'
        C. 正常 LLM 结论仍正常缓存 -> 二次命中缓存=True
```

危害在于它**沉默且不可自愈**：运维发现指标下滑后重跑，缓存原样返回旧的降级结论。
现在判定条件收紧为「`llm` 开头且不含 `heuristic`」。

### 1.2 升级复核掩盖了真实结论来源（P0）

`_quality_gated_fast` 两处升级分支都无条件执行 `escalated.source = "llm-escalated"`。
若升级后的工具回路同样没拿到可解析 JSON，结论其实来自启发式兜底，却被贴上 LLM 标签：

```
修复前  B. 升级路径下同样故障 source='llm-escalated'
修复后  B. 升级路径下同样故障 source='llm-escalated+heuristic'
```

`batch_eval` 的 `source` 列和 `analyze_flags.py` 的升级统计都依赖这个字段做误差归因，
失真会让「升级复核有没有用」的结论本身不可信。`analyze_flags` 用 `"escalated" in source`
匹配，新值仍能正确计入。

### 1.3 `不合规` 被判成合规标签（P0）

`labels.is_compliant_label` 对 `_COMPLIANT_HINTS` 做无边界子串匹配，否定式标签因此被吞掉：

```
修复前  '不合规'                    is_compliant=True
        '非正常营销，引流第三方平台'   is_compliant=True
        '疑似不合规，加微信引流'       is_compliant=True
修复后  三者均为 False，而 '合规招商加盟'/'正常，对本人催收' 仍为 True
```

这个函数同时被三处消费，影响面比看上去大：

- `batch_eval._report` 用它算 `expected_v`，被误判为合规的真违规样本会让模型的正确判定计入 **FP**，
  精确率被系统性压低，同时这些样本从召回分母里消失；
- `reflect.classify_conflict` / `bucket_conflict` 用它分桶，会把真违规样本导向错误的回标建议；
- `agent._knn_conflict` 用它做 kNN 判例冲突信号，邻居标签读反会让软信号失效。

### 1.4 客户端错误也走满重试与退避（P0）

`LLMClient._create_with_retry` 对所有异常一视同仁地退避重试：

```
修复前  401 鉴权失败    实际请求次数=3  耗时=6.0s
        400 上下文超长  实际请求次数=3  耗时=6.0s
        429 限流        实际请求次数=3  耗时=6.0s
修复后  401 鉴权失败    实际请求次数=1  耗时=0.0s
        400 上下文超长  实际请求次数=1  耗时=0.0s
        429 限流        实际请求次数=3  耗时=6.1s   # 限流仍退避重试，且已加抖动
```

Key 配错或模型名写错时，每条样本要白付 3 次请求和 6s 退避才失败；批量跑 2000 条就是 3 小时的纯等待。
新增 `is_retryable()`：优先读结构化 `status_code`，缺失时从异常文案兜底解析，
`{400,401,403,404,405,413,422}` 不重试，429/5xx/无状态码的网络异常仍重试。

同时给退避加了抖动（`backoff × 2^i × [0.5, 1.5)`）。原先所有 worker 撞限流后等长退避，
会同步醒来再次撞墙，并发越高越明显。

### 1.5 单次质检内的重复检索（P1）

一次快速模式质检会重复检索同一批索引：判例库 3 次、技能库 2 次、规范 1 次。

```
修复前  判正常: LLM调用=1  索引search次数=6  ngram处理字符放大 5.6x
修复后  判正常: LLM调用=1  索引search次数=3  ngram处理字符放大 2.6x
```

重复来源：`_inspect_fast` 已经检索过判例和技能，`_hard_signals` 又跑一次完整
`heuristic.inspect`（其检索结果只用于拼 `analysis_thought`，在信号检测中被丢弃），
`_soft_signals` 的 kNN 冲突和涉诈路由冲突再各跑一次；软信号触发时自一致性采样
还会把整套检索再重复 K-1 遍。

修法是引入 `_FastContext`，把 `clipped` / 技能路由 / 判例检索算一次后在各处复用，
并给 `HeuristicInspector.inspect` 加 `include_similar=False`。`QcAgent` 在
`batch_eval` 中被多线程共享，因此上下文按调用传递，未引入任何实例级可变状态。

端到端效果（3000 条语料、1500 字文档、LLM 用替身以剔除网络耗时）：

```
BASE      harness CPU 开销：485 ms/条
优化后    harness CPU 开销：235 ms/条
```

**行为不变性验证**：对 `eval_fresh_cases.csv` 28 条 × 2 种结论（分别触发软信号采样路径和
硬信号升级路径），记录送往 LLM 的全部 112 次调用的完整 messages 与 56 条最终结论，
优化前后**逐字节一致**。

## 2. 建议优先处理

### 2.1 检索层在真实语料规模下会成为吞吐瓶颈

`TfidfIndex` 为字符 2-3gram 建全量倒排表，且 `CaseStore.__init__` 在构造时同步 `fit`，
索引不落盘。仓库自带语料只有 12/28 条，掩盖了真实规模（README 与工具描述均称「数千条」）
的表现。用真实中文语料拼装 2000 字文档实测：

| 语料规模 | 建索引 | 索引峰值内存 | 单次检索 |
|---|---|---|---|
| 500 条 | 5.6s | 274 MB | 37 ms |
| 2000 条 | 23.3s | 1074 MB | 137 ms |
| 5000 条 | 61.5s | 2676 MB | 564 ms |

三个后果：

1. **启动成本**：`inspect_text.py` 每跑一条都要重建索引。5000 条语料下，质检 1 条要先等 61s。
2. **内存**：2.7GB 常驻。`retrieval.py` 文档字符串里「5k 文档 135ms→16ms」的基准显然基于
   短文档，与 2000 字转写的实际表现差一个数量级，建议一并订正以免误导后续调优。
3. **吞吐**：检索是纯 Python、持有 GIL。§1.5 优化后每条仍有 1 次判例检索 + 1 次启发式检索
   ≈ 1.1s 的串行 CPU。`ThreadPoolExecutor` 只能并行等待网络，无法并行这部分，
   于是无论 `--workers` 调多大，吞吐上限都被压在约 1 条/秒。

建议按代价从低到高：

- **索引持久化**：`fit` 结果按语料文件 mtime+size 做指纹，pickle 到 `.cache/`，
  启动时命中则直接加载。消除重复建索引，改动局限在 `TfidfIndex` 与 `CaseStore`。
- **裁剪倒排表**：对 df 过高的 gram（如出现在 >50% 文档中）不建倒排项。这类 gram
  对余弦相似度贡献接近 0（idf≈0）却占据绝大部分 postings，内存与检索时间应能同时下降一个量级。
- **进程级并行**：把批量评估的 worker 从线程改为进程（或把检索移出 GIL），
  才能让 `--workers` 对这部分真正生效。

关于 README TODO #3（换 jieba / scikit-learn / faiss）：`retrieval.py` 顶部已论证过
jieba 在 ASR 噪声下召回更差、faiss 在 TF-IDF 上无质量收益，这个判断依然成立，
上面三条也都不需要引入依赖。真要提升召回质量，正确路径仍是文档里写的——
换中文向量模型顶掉 `fit/search` 的实现，上层接口不变。

### 2.2 可接受类目集被稀释，类目准确率被高估

`labels.normalize_label` 注释写着「按优先级匹配」，实现却是把 `_KEYWORD_TO_CATEGORY`
的**全部**命中并入集合，而 `category_matches` 只要预测落入集合就算对：

```
'加微信推广贷款投资' -> ['企业营销与招商服务', '引流第三方平台', '证券投资类', '贷款相关']
   预测=证券投资类       判为正确=True
   预测=贷款相关         判为正确=True
   预测=引流第三方平台    判为正确=True
   预测=企业营销与招商服务 判为正确=True
```

一条 9 个字的人工标签让 4 个互斥类目全都算对。人工标签越啰嗦，判对越容易，
README 里的类目准确率因此偏乐观。

建议按 `_KEYWORD_TO_CATEGORY` 的列表顺序真正实现优先级（首个命中的类目独占，
其余仅在明确共存时保留），或至少在 `batch_eval` 里对 `|acceptable| > 1` 的样本单列一档统计，
让「宽口径判对」与「唯一判对」分开可见。这会让指标下降，但下降的是虚高部分。

## 3. 工程健壮性

### 3.1 长任务的结果落盘时机

`batch_eval.py` 在全部样本跑完后才写 `results.csv`。中途 Ctrl-C 或 OOM，
已完成的结果全部丢失（缓存保住了 LLM 花费，但指标要重跑）。
`scan_conflicts` 同理。建议改为流式追加写，或每 N 条落盘一次分片。

另外两处并发提交都是一次性 `submit` 全部任务并把结果留在内存
（`batch_eval.py` 的 `futures` 字典、`reflect.scan_conflicts` 的 `futures` 列表），
十万级语料下会有明显内存压力，建议改成有界的分批提交。

### 3.2 反射链路的静默失败

`reflect.py` 有三处会让 `--apply` 悄悄写错东西：

- `reflect()` 里 `except Exception: pass` 吞掉 LLM 反射的全部异常后回退启发式，
  连一行日志都没有，无法区分「LLM 没配」和「LLM 一直在报错」；
- `_reflect_llm` 的 `json.loads(_first_json(...))` 没有 `JSONDecodeError` 保护；
- `_first_json` 用贪婪的 `r"\{.*\}"`，模型输出里出现多个 JSON 对象时会从第一个 `{`
  匹配到最后一个 `}`，拿到一段非法串。`agent.py` 里已有更稳的 `_extract_json`
  （括号配平 + 字符串态跟踪 + 尾逗号容错），应直接复用而不是另写一个弱版本。

考虑到 `--apply` 会真的改写 `knowledge/rules.json` 和技能文件的错题本，这里的静默失败风险偏高。

### 3.3 测试覆盖的空白

85 项单测（本次新增 10 项）全部离线运行，但 `QcAgent` 的三条主路径
——`_inspect_fast`、`_inspect_with_llm` 工具回路、`_quality_gated_fast` 升级链——
此前完全没有覆盖，因为缺少 LLM 替身。本次已经引入 `_StubLLM` 并覆盖了缓存与升级标记，
建议沿这条路继续补：工具回路的多轮 `tool_calls` 往返、回合用尽后的 `_JSON_FORCE` 兜底、
`_repair_json_with_llm` 修复成功/失败两个分支。

仓库没有 `.github/`，即无 CI。`python3 -m unittest tests.test_qc_agent` 3.3s 跑完且零依赖，
接一个最小 workflow 的成本几乎为零，收益是 `rules.json` / 技能文件改动后的自动回归。

`data/eval_fresh_cases.csv` 这份 28 条回归集目前只在人工跑 `batch_eval` 时用到，
建议在离线（启发式）模式下把它固化成断言，守住 README 第 10 节记录的口径。

### 3.4 其它

- `KnowledgeBase.load_rules` 对 `rules.json` 解析失败会抛未捕获异常，
  而 `--apply` 恰好会写这个文件；写坏一次，所有入口（含离线启发式）全部起不来。
  建议解析失败时报错并回退到内置空规则，至少让 CLI 能启动并给出可读提示。
- `ResultCache._load` 缓存损坏时静默清空（`except Exception: self._mem = {}`），
  用户只会看到「缓存突然全部失效」。补一行 warning 即可。
- `dedup` 的 `simhash` 实测 18ms/条（2000 字），5000 条约 89s 前置开销。
  瓶颈是 `_hash64` 之后对每个 gram 再循环 64 位。README 已说明 ASR 语料去重收益有限，
  所以这更像是「`--dedup` 要用就得先接受 90s 起步」的已知代价，值得在帮助文本里点明。

## 4. 结构与重复

这部分不影响正确性，属于维护成本：

- **启发式规则与 `rules.json` 双源**。`heuristic.py` 顶部硬编码了
  `_VIOLATION_DEFAULT_RISK`、`_HIGH_RISK_TRIGGERS`、`_MEDIUM_RISK_TRIGGERS`
  和若干正则，与 `rules.json` 的 `risk_rules` / `keywords` 表达同一套口径。
  改规范时要改两处，且没有任何机制保证它们一致——最容易出现的漂移是
  `rules.json` 更新了风险等级而启发式默认值没跟上。可以考虑让默认风险等级从
  `rules.json` 派生，只把正则类判别留在代码里。
- **两套 brief 拼装重复**。`knowledge_base.slim_brief()` 与 `rules_brief()`
  的业务口径判定表渲染逻辑几乎逐行相同，`scripts/build_skills.py` 里还有第三份。
  抽一个 `_render_decision_table(rows)` 即可。
- **`QcAgent` 职责过重**。526 行里混了 JSON 提取、质量门控、两条 LLM 路径和结果归一化。
  按现在的规模还能读，但 JSON 提取（`_extract_json` 及其辅助函数，约 70 行纯函数）
  完全独立，拆成 `json_utils.py` 后 `reflect.py` 也能顺带复用（见 §3.2）。
- **缓存指纹用错了 brief**。`agent.py` 用 `kb.rules_brief()` 参与指纹，
  但 skills 模式下真正进 prompt 的是 `slim_brief()`。`rules_brief` 是超集所以目前不会漏失效，
  属于可以工作但语义对不上的地方。
